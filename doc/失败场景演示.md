# 失败场景演示

## 目标
- 演示系统不是“只跑成功路径”，而是对异常路径有明确处理和可追踪能力。

## 场景 1：档期已满，预约失败
1. 先把某个档期占满（可先跑一次预约成功流程）。
2. 再次调用：`POST /app/booking/create`
3. 预期：
- HTTP 200
- 业务 `code=201`
- `message` 提示档期可能已满

说明：这是业务拒绝，不是系统异常。

## 场景 2：支付回调重复通知（幂等）
1. 第一次：`POST /app/pay/mock-notify`（同一个 `payNo`）
2. 第二次：再调一次同样请求
3. 查询：`GET /admin/pay/callback/list?payNo=xxx`
4. 预期：
- 第一次 `processResult=PROCESSED`
- 第二次 `processResult=IDEMPOTENT`

说明：证明“重复回调不会重复入账”。

## 场景 3：退款前置条件不满足
1. 对未支付报名直接调：`POST /app/course/refund`
2. 预期：
- HTTP 200
- 业务 `code=201`
- 提示仅支持已支付报名退款

说明：证明状态机约束生效。

## 场景 4：上传参数错误
1. 上传接口不传 `file` 或路径错误
2. 调用：`POST /admin/video/upload`
3. 预期：
- 返回失败，日志有 `MissingServletRequestPartException` 或参数错误信息

说明：证明文件上传有参数校验，不会吞错。

## 演示收尾建议
- 最后执行一次 `GET /admin/refund/list` 和 `GET /admin/pay/callback/list`。
- 强调：异常路径也会被记录，支持追溯。
