# 健身平台简历项目亮点（真实增强版）

## 1. 当前项目定位

该项目适合定位为具备以下能力的工程型单体项目：

- `multi-instance deployment`
- `concurrency control`
- `cache protection`
- `idempotency governance`
- `observability`
- `automated regression`

更准确的包装方式：

- 工程型单体项目
- 中小规模高并发治理场景
- 以 `Nginx + Redis + MySQL + Caffeine` 为核心的一致性与性能优化项目

不建议包装为：

- 超大规模分布式系统
- 微服务平台
- AI / RAG 平台

## 2. 简历项目介绍写法

### 2.1 一句话版本

基于 `Spring Boot + MySQL + Redis + Caffeine + Nginx` 构建运动健康管理平台，围绕课程报名、教练预约、支付回调等高冲突场景，落地 `dual-instance deployment`、`three-layer concurrency control`、多级缓存近实时失效、幂等治理与自动化回归验证。

### 2.2 两句话版本

负责运动健康管理平台后端核心链路开发与稳定性治理，覆盖训练计划、课程报名、教练预约、支付回调、RBAC、运营位、任务补偿与审计日志等模块。针对多实例部署下的并发冲突与缓存热点问题，设计并实现 `TokenVersion-enhanced stateless JWT authentication`、Redis 短幂等/短锁/限流、数据库条件更新与唯一索引兜底，以及 `Caffeine + Redis + Redis Pub/Sub` 多级缓存近实时失效，并通过 Postman/Newman + GitHub Actions 建立 `end-to-end regression pipeline`。

## 3. 推荐技术亮点

1. 基于 `Nginx upstream + dual-instance deployment` 完成 `web-app` 双实例部署，结合 `TokenVersion-enhanced stateless JWT authentication` 解决多实例下登录态共享、账号禁用和密码重置后的 token 失效问题。
2. 针对课程报名、教练预约、支付回调等高冲突场景，设计并落地 `three-layer concurrency control`：应用层 `idempotency guard`、Redis `distributed short lock / rate limiting`、数据库 `conditional update + unique index fallback`。
3. 使用 Redis 实现登录、短信发送、报名、预约等接口的 `fixed-window rate limiting` 与 `short-lived idempotency key`，降低撞库、重复点击和重试风暴带来的无效请求。
4. 针对课程名额与教练档期，采用数据库 `atomic conditional update`（`booked_count < capacity`）控制资源竞争，保证多实例并发下不超卖、不超约。
5. 针对支付异步通知，落地 `callback idempotency` 方案：`Redis short lock + payment status check + DB idempotency fallback`，确保重复回调不重复入账。
6. 针对 Banner、Notice、SystemConfig、Course List、Plan Detail Static 等读多写少场景，落地 `Caffeine + Redis + Redis Pub/Sub` 多级缓存方案，通过事务后删除 Redis、广播本地缓存失效实现近实时一致。
7. 在缓存链路中补充 `Cache-Aside`、`TTL jitter`、`null-object caching`、`hotspot cache rebuild protection`，提升热点读取稳定性并降低缓存击穿风险。
8. 建立 `observability + regression validation` 机制：统一 `traceId + userId + instanceId` 链路日志、支付回调审计、任务运行记录、并发脚本验证、Postman/Newman + GitHub Actions 自动化回归，保证多实例与并发方案可验证、可复现。

## 4. 术语与实现映射

| 术语 | 当前项目中的真实落地 | 解决的问题 |
| --- | --- | --- |
| `dual-instance deployment` | `web-app` 双实例 + Nginx `upstream` 轮询 | 解决单点部署与横向扩展问题 |
| `TokenVersion-enhanced stateless JWT authentication` | App/Admin 统一 JWT + `tokenVersion` 校验 | 解决多实例下无状态认证与即时失效问题 |
| `three-layer concurrency control` | 应用层幂等 + Redis 辅助互斥 + DB 最终兜底 | 解决多实例并发冲突 |
| `fixed-window rate limiting` | 登录、短信发送、敏感写接口限流 | 解决撞库、刷接口、重试风暴 |
| `short-lived idempotency key` | 报名、预约短幂等键 | 解决重复点击和重复提交 |
| `distributed short lock` | 支付回调短锁、缓存重建短锁、任务锁 | 解决跨实例并发处理冲突 |
| `atomic conditional update` | `booked_count < capacity` 条件更新 | 解决超卖、超约 |
| `unique index fallback` | 重复报名、重复预约、回调兜底 | 解决 Redis 失效后的最终一致性 |
| `Caffeine + Redis + Redis Pub/Sub` | 本地缓存 + 共享缓存 + 近实时失效广播 | 解决双实例下静态缓存一致性问题 |
| `Cache-Aside` | Banner、公告、系统配置、课程列表、计划详情静态缓存 | 解决读多写少场景的性能问题 |
| `TTL jitter` | 缓存过期时间抖动 | 解决同一时刻集中失效 |
| `null-object caching` | 空值缓存 | 解决缓存穿透 |
| `hotspot cache rebuild protection` | 计划详情互斥重建 | 解决热点 key 击穿 |
| `graceful degradation` | Redis 不可用时读回源、写兜底 | 解决中间件短暂异常导致的整体不可用 |
| `runtime observability` | `traceId + userId + instanceId` 链路日志 | 解决双实例下问题定位困难 |
| `end-to-end regression pipeline` | Postman/Newman + GitHub Actions | 解决多链路改动后的回归成本问题 |

## 7. 面试时的推荐主线

1. 先讲部署形态：`dual-instance deployment + stateless JWT authentication`
2. 再讲并发治理：`idempotency guard + Redis short lock / rate limiting + DB conditional update / unique index fallback`
3. 再讲缓存设计：`Caffeine + Redis + Redis Pub/Sub + Cache-Aside + TTL jitter`
4. 最后讲工程闭环：`runtime observability + automated regression + callback audit + compensation task`

## 8. 可直接贴进简历的亮点示例

- 基于 `Nginx upstream + dual-instance deployment` 完成 App 服务双实例部署，结合 `TokenVersion-enhanced stateless JWT authentication` 实现多实例下无状态登录鉴权与强制失效控制。
- 围绕课程报名、教练预约、支付回调等高冲突场景，设计 `three-layer concurrency control`，通过应用层幂等、Redis 短锁/限流、数据库条件更新与唯一索引兜底保障最终一致性。
- 基于 `Caffeine + Redis + Redis Pub/Sub` 落地静态读模型多级缓存，通过事务提交后删除 Redis 并广播本地缓存失效，实现双实例下的近实时缓存一致性。
- 通过 `traceId + userId + instanceId` 链路日志、支付回调审计、任务运行记录、并发验证脚本与 Postman/Newman + GitHub Actions 自动化回归，建立可观测、可验证、可复现的工程闭环。
