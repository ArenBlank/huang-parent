# 轻量 Redis 锁设计说明

## 定位

本项目使用的是轻量 Redis 分布式锁增强方案，不是 Redisson 完整锁实现。

设计目标不是覆盖所有分布式锁特性，而是服务当前业务场景：

- 缓存击穿保护
- 支付回调并发削峰
- 定时任务互斥执行

这个方案强调按场景取舍，而不是为了技术栈完整度引入更重的中间件抽象。

## 当前已支持能力

- 加锁原子性
  - 使用 `SET key value NX EX`
  - Redis 单命令完成抢锁和 TTL 设置
- 安全释放
  - 使用 Lua compare-and-delete
  - 只有锁 value 与当前 token 匹配时才删除
- 锁结果显式建模
  - `ACQUIRED`：拿到锁
  - `BUSY`：锁已被别人持有
  - `DEGRADED`：Redis 不可用或当前锁能力降级
- 业务降级策略分场景收口
  - 定时任务默认跳过，避免重复执行
  - 支付回调允许退化到数据库幂等兜底
- 缓存重建短等待
  - 抢不到缓存锁时短暂随机退避后重读缓存
  - 不把缓存锁扩展成通用阻塞等待锁

## 为什么没有直接上 Redisson

当前场景不强依赖以下能力：

- 可重入锁
- watchdog 自动续期
- 通用阻塞等待锁
- 公平锁、读写锁等复杂语义

如果直接引入 Redisson，确实可以更快获得这些特性，但也会让项目叙事变成“依赖框架提供锁能力”。

当前方案更适合这个项目的表达方式：

- 知道 Redis 分布式锁的基础实现方式
- 知道 Lua 在锁释放中的价值
- 知道 Redis 锁不是业务一致性的最终兜底
- 知道什么时候应该升级到 Redisson

## 业务边界

### 缓存击穿

目标是避免热点 key 在失效瞬间把并发请求全部打到数据库。

这里不要求可重入，也不要求长时间持锁。轻量锁足够。

### 支付回调

Redis 锁只负责并发削峰，不负责最终一致性。

最终一致性由数据库条件更新兜底：

- 仅当 `payment_record.pay_status != 'PAID'` 时允许更新为 `PAID`
- 更新成功的请求才算首个处理者
- 更新失败后重新读取，如果已经是 `PAID`，按幂等成功处理

因此，即使 Redis 锁降级或提前过期，也不会把支付成功逻辑重复落库。

### 定时任务

当前任务都是固定 TTL 的轻量互斥任务。

- 锁忙时跳过
- Redis 降级时默认跳过
- 如后续出现长耗时任务，再考虑续期机制或切换 Redisson watchdog

## 当前明确不支持

- 可重入
- watchdog 自动续期
- 通用阻塞重试锁
- 公平锁
- 完整 Redisson 兼容语义

## 何时应该升级

当业务明确出现以下需求时，可以考虑升级到 Redisson：

- 同线程重复进入同一业务锁
- 任务执行时间明显超过固定 TTL
- 需要统一阻塞等待和超时唤醒语义
- 需要更复杂的分布式同步原语

在那之前，轻量实现加上明确边界和数据库兜底，就是更合适的工程选择。
