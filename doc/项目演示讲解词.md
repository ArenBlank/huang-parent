# 项目演示讲解词

更新时间：2026-03-20  
适用版本：`V3`  
用途：面试演示、作品集讲解、阶段性交付汇报

## 1. 一句话介绍

这是一个健身平台项目，分为 `Admin 管理端` 和 `App 用户端` 两部分，核心业务覆盖训练计划、课程报名、教练预约、支付退款、视频素材管理和运营内容管理。

## 2. 开场讲法

如果你只想先用一句话把项目讲清楚，可以直接这样说：

“这个项目我做的是一个健身平台，分成管理端和用户端。用户端负责计划训练、课程报名、教练预约、订单和个人资料；管理端负责课程、视频、运营内容、权限和日志。我重点不是只把页面做出来，而是把核心业务闭环、权限边界、回归验证和可演示性一起做完整。”

## 3. 3 分钟版讲法

### 3.1 先讲目标

“这个项目的目标不是单纯堆页面，而是做一个能演示、能回归、能继续迭代的完整作品。  
我把重点放在三件事上：第一是核心业务闭环能跑通，第二是权限和日志这些工程能力要有，第三是要能通过自动化和联调验证证明它不是只能看不能用。”

### 3.2 再讲结构

“整体上分成四部分：

- 后端有 `web-admin` 和 `web-app`
- 前端有 `frontend` 和 `frontend-app`
- 数据层用的是 MySQL、Redis、MinIO
- 回归层用 Postman + Newman + GitHub CI”

### 3.3 最后讲结果

“目前这版已经做到：

- API 核心回归和全量回归都通过
- 前端构建通过
- Admin 和 App 的核心主链都做了真实浏览器联调
- 所以当前版本已经可以作为演示基线和封版基线”

## 4. 5 到 10 分钟演示顺序

### 4.1 第一段：先讲验证结果

建议先说这句：

“我先不只讲页面，我先讲验证结果。现在核心 API 回归是 `39 requests / 143 assertions / 0 failed`，全量回归是 `127 requests / 389 assertions / 0 failed`。另外我还做了浏览器真实联调，不只是接口调通，而是前端点击后真正请求后端并完成状态流转。”

### 4.2 第二段：演示 Admin

建议操作顺序：

1. 登录 Admin
2. 打开权限中心
3. 打开视频素材，点击刷新
4. 打开订单，点一条查看详情
5. 打开操作日志，做一次筛选查询

对应讲法：

“管理端我主要展示四块：权限、资源、订单和日志。  
权限中心说明我不是只做了静态页面，后台权限模型是落地的。  
视频素材说明内容资源是可以管理的。  
订单详情说明支付和退款状态不是散的，是能聚合展示的。  
操作日志说明关键操作是可追踪的，这对回归和排障很重要。”

### 4.3 第三段：演示 App 预约闭环

建议操作顺序：

1. 登录 App
2. 首页读取系统配置
3. 进入教练预约
4. 提交预约
5. 模拟支付
6. 确认完成
7. 提交评价

对应讲法：

“这条链我想证明的是用户端不是页面拼起来的，而是有完整状态流转。  
从预约创建，到支付成功，到服务完成，再到评价提交，前后端都能真实联动。”

### 4.4 第四段：演示 App 课程闭环

建议操作顺序：

1. 进入课程页
2. 提交报名
3. 模拟支付
4. 发起退款

对应讲法：

“课程这条链我重点展示的是报名、支付和退款。  
这样就能看出两个核心业务闭环都具备：一个是预约闭环，一个是课程交易闭环。”

## 5. 工程亮点讲法

建议挑下面 4 个讲，不要一次讲太多。

### 5.1 亮点一：不是只有 CRUD

“这个项目我有意识避开了只做增删改查。  
我把预约、支付、完成、评价，和报名、支付、退款这些状态链做完整了，所以它更像一个真实业务系统。”

### 5.2 亮点二：权限和审计一起做

“我把 RBAC 和操作日志一起做了。  
这样不仅能控制谁能访问，还能追踪谁做了什么，对后台系统更合理。”

### 5.3 亮点三：自动化回归不是摆设

“我没有停在‘能调通一次’这个层面，而是把核心链路和全量链路都沉淀成 Newman 回归和 CI。  
这意味着每次改动后都可以快速验证有没有回归。”

### 5.4 亮点四：做了真实浏览器联调

“我还额外做了浏览器级联调。  
这一步能验证前端按钮、路由、token、字段映射、后端返回和页面状态更新是不是全都真的通了。  
它比单纯跑 Postman 更接近真实使用场景。”

## 6. 如果被问“现在是不是完全没 bug”

建议这样回答：

“不能说 100% 没 bug。  
更准确的说法是：已覆盖的核心场景没有回归，主链已经证明可用。  
CI 全绿和浏览器联调通过，说明当前版本具备稳定基线，但不等于所有未知边角场景都绝对没有问题。”

## 7. 如果被问“为什么 CI 全绿还要做前端联调”

建议这样回答：

“因为 CI 里的 API 回归主要验证接口行为正确。  
但真实前端联调还会暴露另外一类问题，比如 token 没带上、字段名不一致、页面没刷新、路由没跳对、按钮触发错接口。  
所以 API 回归和浏览器联调是两层不同的验证，结合起来更可靠。”

## 8. 如果被问“这版还有哪些边界”

建议这样回答：

“这版我刻意收边界了。  
核心主链我已经做完整，但没有继续扩到所有后台维护页、所有认证扩展页和所有异常分支。  
我把它控制在一个能演示、能回归、能继续迭代的稳定版本，而不是无限堆功能。”

## 9. 结束语讲法

最后建议这样收：

“如果从作品集和面试展示角度看，这一版已经足够说明问题：  
它不是一个只会展示页面的项目，而是一个核心业务闭环完整、权限和日志具备、自动化和联调验证也做了的工程化项目。  
如果后面继续，我会按主题继续拆分，而不是无边界扩张。”
