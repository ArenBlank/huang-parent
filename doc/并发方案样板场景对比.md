# 并发方案样板场景对比

## 1. 目标
这份文档把项目里最值得学习的 4 类并发方案放到同一张桌子上比较：
- JVM 本地锁
- Redis 短锁/短幂等
- 数据库条件更新
- 数据库唯一索引兜底

重点不是“都用上”，而是知道每种方案解决什么问题、解决不到什么程度、失败时靠谁兜底。

## 2. 四类方案总表

| 方案 | 解决的问题 | 适合场景 | 不适合场景 | 本项目对应点 |
| --- | --- | --- | --- | --- |
| JVM 本地锁 | 单实例内线程竞争 | 学习线程安全、单机场景 | 双实例、跨 JVM | 仅作为学习样板，不建议线上主用 |
| Redis 短锁/短幂等 | 跨实例短时间重复请求 | 重复点击、热点缓存重建、重复回调 | 最终一致性强约束 | 计划详情缓存锁、报名/预约幂等、支付回调短锁 |
| 数据库条件更新 | 强一致资源扣减 | 名额、库存、状态推进 | 复杂长事务排队 | `booked_count < capacity` |
| 数据库唯一索引 | 最终兜底防重复写入 | 报名、预约、支付回调幂等键 | 高并发下做第一道门 | `course_enrollment`、`coach_booking`、`payment_record.callback_idempotency_key` |

## 3. 四个样板场景

### 3.1 样板一：JVM 本地锁
问题：
- 同一个实例里，多个线程同时修改同一份内存状态。

结论：
- 只能保护当前 JVM。
- 一旦部署成 `web-app:8081` 和 `web-app:8082`，两个实例之间彼此看不见。

学习价值：
- 非常适合建立“线程安全”和“临界区”的直觉。
- 但不能误认为它能解决线上双实例并发。

建议演练：
- 本地写一个简单 Demo，用 `synchronized` 对同一计数器加锁。
- 再把请求分别打到两个实例，就能直观看到本地锁没有跨实例能力。

### 3.2 样板二：Redis 短锁/短幂等
问题：
- 用户重复点击提交。
- 同一热点缓存同时失效，多个实例同时回源数据库。
- 支付平台短时间重复回调。

本项目落点：
- 计划详情缓存互斥重建：`PlanBizService`
- 报名短幂等：`CourseController`
- 预约短幂等：`BookingController`
- 支付回调短锁：`PaymentCallbackBizService`

边界：
- Redis 适合挡“短时间内的重复操作”。
- Redis 不是最终正确性的来源，不能单独承担交易一致性。

失败模式：
- Redis 不可用时，幂等/限流会降级放行。
- 因此数据库兜底必须继续保留。

### 3.3 样板三：数据库条件更新
问题：
- 报名名额、预约名额这类资源不能超卖。

本项目落点：
- 课程报名：更新 `course_schedule.booked_count`
- 教练预约：更新 `coach_schedule.booked_count`

关键思想：
- 把“判断是否还有名额”和“扣减/占用名额”合并成一条 SQL。
- 避免先查后改带来的竞态。

代表语句：
- `booked_count < capacity`

优点：
- 强一致，简单直接。
- 对双实例天然有效，因为最终都落在同一个数据库上。

### 3.4 样板四：唯一索引兜底
问题：
- 即使前面已经做了 Redis 幂等和业务校验，仍可能因为重试、网络抖动、并发穿透而出现重复写库尝试。

本项目落点：
- `course_enrollment` 唯一索引
- `coach_booking` 唯一索引
- `payment_record.callback_idempotency_key` 唯一索引

定位：
- 它不是最好的第一道防线。
- 但它是最可靠的最后一道门。

优点：
- 最终正确性强。
- 对应用实例数量不敏感。

代价：
- 重复请求会真正打到数据库。
- 用户体验通常不如入口幂等那么友好。

## 4. 推荐组合，而不是单押一种

### 4.1 报名/预约
- 第一层：Redis 短幂等，挡重复点击和重试风暴
- 第二层：数据库条件更新，保证不超卖
- 第三层：唯一索引，兜底防重复落库

### 4.2 支付回调
- 第一层：Redis 短锁，避免两个实例同时处理同一 `payNo`
- 第二层：支付状态判断
- 第三层：数据库幂等键唯一索引

### 4.3 热点缓存
- 第一层：普通缓存读取
- 第二层：Redis 互斥锁，控制缓存重建
- 第三层：锁失败时短暂等待，再不行就回源数据库

## 5. 如何在本项目里做学习型演练

仓库内已经补了一个最小学习型对比测试：
- `common/src/test/java/com/huang/common/learning/ConcurrencyLearningTest.java`

它会直接对比三种结果：
- 无幂等：大量请求会一起成功
- Redis 风格入口幂等：只有 1 次真正打到“数据库”
- 只有数据库唯一索引兜底：最终也只成功 1 次，但所有请求都会打到“数据库”

### 5.1 双实例观察
```powershell
powershell -ExecutionPolicy Bypass -File start-all.ps1
powershell -ExecutionPolicy Bypass -File tests/check-dual-app-routing.ps1
```

### 5.2 报名/预约并发观察
```powershell
$body = '{"scheduleId":1}'
powershell -ExecutionPolicy Bypass -File tests/invoke-concurrent-requests.ps1 `
  -Url "http://app.localhost/app/course/enroll" `
  -Body $body `
  -Token "<jwt>" `
  -Concurrency 10
```

### 5.3 观察重点
- 哪些请求先被 Redis 幂等挡住
- 哪些请求进入数据库后被条件更新拦住
- 是否最终只落一条业务记录
- 两个实例是否都有流量命中

## 6. 最终方法论
- 本地锁解决“单 JVM 线程安全”
- Redis 解决“跨实例短时间协调”
- 数据库条件更新解决“强一致资源竞争”
- 唯一索引解决“最终重复写入兜底”

真正成熟的方案，通常不是四选一，而是按职责组合。
