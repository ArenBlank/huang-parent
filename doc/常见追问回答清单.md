# 常见追问回答清单

更新时间：2026-03-20  
适用版本：`V3`  
用途：面试答辩、项目汇报、验收追问

## 1. 这个项目是做什么的

短答版：

“这是一个健身平台项目，分成 Admin 管理端和 App 用户端，核心覆盖训练计划、课程报名、教练预约、支付退款、视频素材和运营内容管理。”

展开版：

“我想做的不是单纯的页面集合，而是一个有完整业务闭环的项目。  
用户端负责训练、课程、预约、订单和资料；管理端负责课程、视频、内容运营、权限和日志。  
这样既能展示业务设计，也能展示工程化能力。”

## 2. 你这个项目的重点是什么

短答版：

“重点不是页面数量，而是核心闭环、权限边界和验证体系。”

展开版：

“我刻意把重点放在三件事上：  
第一，预约和课程两条主链要完整；  
第二，后台权限和日志要落地；  
第三，要用自动化回归和浏览器联调证明它是真的能用，而不是只能演示静态页面。”

## 3. 现在这版已经做到什么程度

短答版：

“现在已经到可演示、可回归、可封版的程度。”

展开版：

“当前版本 API 核心回归和全量回归都通过，前端构建通过，Admin 和 App 的核心主链也做了真实浏览器联调。
另外，这一版把轻量 Redis 锁补成了更工程化的实现，也把用户端 H5 / 移动端页面继续补齐到了订单详情、教练申请、账户安全这些真实业务页。
所以它已经适合作为作品集、面试演示和阶段性交付基线。”

## 4. CI 全绿说明了什么

短答版：

“说明已覆盖场景没有回归，不说明 100% 没有未知 bug。”

展开版：

“CI 全绿的价值在于：已经纳入回归集合的接口和链路当前是稳定的。  
但它不等于所有边角分支都永远没问题。  
更准确的说法是，已覆盖核心场景通过，当前版本具备稳定基线。”

## 5. 为什么 CI 全绿了还要做前端联调

短答版：

“因为接口正确，不等于前端实际使用一定正确。”

展开版：

“API 回归主要证明接口行为对。  
但真实前端联调还会发现另一类问题，比如 token 没带、字段名对不上、页面没刷新、按钮点错接口、路由跳错。  
所以我把 API 回归和浏览器联调当成两层验证，结合起来更稳。”

## 6. 你怎么证明这个项目不是只会展示页面

短答版：

“我用回归、联调和状态闭环来证明它不是静态演示。”

展开版：

“我不只是把页面搭出来，而是把业务主链做成了真实状态流转。  
比如预约是创建、支付、完成、评价；课程是报名、支付、退款。  
再加上 Newman 回归和浏览器真实点击联调，这能证明它不是纯展示型项目。”

## 7. 这个项目有哪些核心闭环

短答版：

“两个最核心闭环是教练预约闭环和课程交易闭环。”

展开版：

“预约闭环是：创建预约、支付、完成、评价。  
课程闭环是：报名、支付、退款。  
这两条链能体现状态流转、订单联动和前后端协同，是整个项目最有代表性的部分。”

## 8. 权限是怎么做的

短答版：

“权限用的是基于角色的访问控制，资源级接口做了边界约束。”

展开版：

“我做的是 RBAC 这一层，不是复杂策略引擎。  
管理端不同角色对应不同接口和资源范围，前端也有受保护路由。  
这样既能满足后台系统常见需求，又不会把设计做得过重。”

## 9. 为什么要做操作日志

短答版：

“因为后台系统不只要能操作，还要能追踪。”

展开版：

“操作日志的价值主要有两个：  
第一，方便回归和排障，知道谁做了什么；  
第二，让后台系统更像真实业务系统，而不是只做了管理页面。  
这也是我想保留的工程亮点之一。”

## 10. 为什么支付只做了 mock

短答版：

“因为这个阶段的目标是跑通业务闭环和工程结构，不是硬接第三方 SDK。”

展开版：

“真实微信或支付宝接入会把大量工作带到第三方配置、签名、证书和环境联调上。  
当前版本我更关注的是订单状态机、回调幂等、退款联动和可验证性。  
所以用 mock 支付把核心链路先做完整，这对作品集阶段更划算。”

## 11. 这个项目现在能不能上线

短答版：

“可以作为继续迭代的稳定基线，但还不建议直接当正式商业版本上线。”

展开版：

“从结构、闭环和验证上看，它已经具备继续产品化的基础。  
但如果真要正式上线，还需要补更多生产级内容，比如更完整的认证体系、真实支付接入、更细的监控告警、灰度和安全策略。  
所以我会把当前版本定位成稳定基线，而不是直接宣称生产就绪。”

## 12. 你觉得这个项目最有价值的地方是什么

短答版：

“它把业务闭环和工程验证放在一起做了。”

展开版：

“很多项目要么偏页面展示，要么偏接口演示。  
这个项目更有价值的地方是：主链能跑、后台能力在、自动化回归有、浏览器联调也做了。  
它比较完整地体现了从开发到验证的一整套思路。”

## 13. 你这版为什么要收边界

短答版：

“因为项目的目标是形成稳定版本，不是无限扩功能。”

展开版：

“如果继续顺手补页面、补分支、补后台工作台，很容易进入没有终点的状态。  
所以我明确把边界卡在核心闭环、权限、日志、回归和联调这几个点上。  
达到演示和交付目标后就封版，这样版本才是可控的。”

## 14. 如果继续做，下一步做什么

短答版：

“下一步不再混做，而是按主题单独推进。”

展开版：

“如果继续，我只会从下面主题里明确选一个：  
退款审计页、支付回调审计页、用户角色维护页、认证扩展页。  
一次只做一个主题，这样不会把版本重新拖回无边界扩张。”

## 15. 你在这个项目里最重视的工程习惯是什么

短答版：

“我最重视可验证性和边界控制。”

展开版：

“我希望每次改动都能回答两个问题：  
第一，怎么证明它真的可用；  
第二，做到什么程度就该停。  
所以这个项目里我一直在做的事情就是让链路可验证，同时防止项目无限发散。”

## 16. 结束时的收束回答

短答版：

“这版已经足够证明我能把业务、工程和验证一起落地。”

展开版：

“如果从作品集或面试角度看，这一版已经能说明核心问题：  
我不是只会搭页面，也不是只会写接口，而是能把业务闭环、权限边界、日志、回归和联调一起做成一个稳定版本。  
这也是我认为它最能体现能力的地方。”
